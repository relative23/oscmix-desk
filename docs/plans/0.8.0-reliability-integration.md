# 0.8.0: reliability and Linux integration

**Status: implementation started on the maintainer's explicit instruction, 2026-09-25.**
This is the next implementation plan, including the corrections previously
discussed for 0.7.4. No separate 0.7.4 release is planned. The installed and
published baseline remains 0.7.3; this document records targets, not delivered
capabilities. See the [roadmap](../ROADMAP.md).

Progress: the working tree and `04ba141` baseline have been checked. N9's
historical source assessment is recorded privately. N0/N1 corrections now
share revocable observations and select writes by operation intent, including
retained structural/partner dependencies and accurate recovery messages.
Interim `make check`: 2017 passed, two empty parameter sets skipped in the
read-only subfamily tests; separate coverage: 98%.
These runs used the current development code and simulated I/O; they are not
the final N8 gates. N2's implementation decision is
[ADR 0030](../decisions/0030-backend-owned-control.md). No 0.8.0 hardware
measurement, new-platform qualification, release or local installation is
claimed. The maintainer selected a new project signing key for N6; key setup
and package-source publication remain to be done.

The target is one Fireface UCX II across Linux distribution families.
The existing upstream GTK mixer belongs to the integration work. A new desk
GUI, physical multi-device qualification and other Fireface models remain
separate. Preserve the standard-library Python runtime and upstream's device
protocol implementation. Do not introduce a second protocol stack, continuous
automatic reconciliation or an audio/clock manager to meet this plan.

## Baseline and order

The runtime at `main` (`04ba141`) is identical to release commit `3397ecb`.
Controlled probes against the imported runtime, with sockets disabled and
simulated I/O, reproduce two open correctness cases:

- `await_link_echo()` returns confirmed for A=1, A=0, B=1 when A=1/B=1
  are required, in both separate deliveries and one batch.
  `_link_sync_observer()` also releases a mix write after that sequence.
- `reconcile_now()` with a missing REMEMBER `/output/5/volume` report
  selects the configured -6 dB for writing. An observed -30 dB deviation
  is protected; an unavailable receiver causes no apply. Explicit PIN
  retains its write authority. This is a write-selection issue after the
  initial apply, not a newly introduced 0.7.3 regression claim.

These results validate the control-flow cases, not a physical audio effect.
The general verifier already replaces contradicted confirmations; the two
link observers have not yet adopted that rule. Existing qualification remains
historical evidence for its exact revision.

| Stage | Work | Exit condition |
| --- | --- | --- |
| 1 | N9 baseline assessment and N0/N1 observation/write intent | The actual historical source changes are assessed; reproduced defects have regressions that fail on the baseline and pass through the real apply/reconcile paths after correction. |
| 2 | N2/N3: backend contract and capability investigation | A concrete transport/ownership design and reproducible capability results settle the implementation route before a new coordinator or backend pin is adopted. |
| 3 | N2/N3: runtime integration | Actual GTK and desk cooperate under the same lifecycle and write-order contract; newly claimed read-back is measured. |
| 4 | N4/N5/N6: installation and distribution | Named init/host targets and signed repositories pass their real lifecycle and package-manager checks. |

Keep the correctness changes separately reviewable from transport and packaging.
N4/N5/N6 preparation can use the settled stage-2 interface; final qualification
must follow the final runtime. New findings join this plan with a reproducer
and an explicit acceptance condition. Private review material is not a release
artifact.

## Contracts retained from 0.7.2 and 0.7.3

These implemented behaviors are acceptance requirements for 0.8.0, not another
backlog of features to rebuild. The historical source comparisons belong to N9;
the final regression checks belong to N8. Existing tests should be reused and
extended only for uncovered cases or changed boundaries.

| Contract | 0.8.0 work and acceptance |
| --- | --- |
| Actual USB/playback mode and device identity before write phases | N0/N2/N3 must retain the guard for every applicable phase and mix reapply. A change before writing refuses the operation; a mid-operation change records sent and pending paths without claiming rollback. |
| Installation, package ownership and upgrade behavior | N4/N5/N6 preserve install-before-activation, user-owned configuration and profile state, complete version pairs and recoverable maintenance fencing. N9 examines whether the adapters share these decisions without duplicating lifecycle logic. |
| Latest decoded report within an open observation window | N0 extends the existing verifier rule consistently to both link observers, including revocation, batch boundaries and invalid decoded values. No atomic snapshot or permanent confirmation is implied. |
| Distinct read-back meanings | N1/N7 retain separate confirmed, observed REMEMBER deviation, PIN mismatch, missing and backend-unreportable results. A REMEMBER value retained without observation gets its own accurate meaning; reports and write selection must agree. |
| Read-only `--status [--json]` | N2/N4/N5/N7 may add diagnosis for the new integration, but status sends no OSC request, binds no socket, opens no PCM stream, starts no session/service and changes no configuration or hardware state. Preserve structured-output and exit semantics. |
| `--dry-run --profile` compares declarations | N1/N7 preserve a write-free preview of previously declared crosspoints omitted by the target. Unknown hardware matrix entries remain unknown; omission never silently mutes or deletes a route. |
| Exact-context upstream GTK launch | N2/N7 preserve device/backend identity checks, GTK prerequisites and connection validation, matching manual-session reuse, explicit service activation and refusal of unrelated listeners or incomplete maintenance. |
| One reply destination and GTK outside the desk lock | N2 replaces this limitation only with a tested reply, writer-order and lifecycle contract. Sharing a receive stream alone is insufficient. |
| Understandable architecture as behavior grows | N9 checks actual source changes and demonstrated complexity independently of software/hardware qualification results. Correct only concrete structural problems; preserve necessary distinctions. |

## N9: architecture assessment from the actual source changes

Assess architecture and code structure on their own evidence. Passing tests,
coverage percentages, CI breadth and hardware measurements remain necessary
qualification, but do not by themselves establish a good abstraction. Release
size, file count and subjective scores likewise establish no structural defect.
This is a required investigation, not a claim that overengineering was proved.

Read `v0.7.1..v0.7.2` and `v0.7.2..v0.7.3` as separate source diffs, following
changed call paths into the unchanged modules they rely on. Cover runtime,
entry points, installer, package staging/setup/guards and service integration;
release notes or diff statistics alone do not finish the task. Inspect in
particular `streams`, `routing`, `verify`, `diagnostics`, `status`, `desktop`,
`launcher`, `preview`, profile/reload outcomes and the installation guards.

For each relevant path, establish:

- Which component owns device identity, observation freshness, effective
  policy, write permission, lifecycle and maintenance state. Identify duplicated
  decisions, conflicting representations and state whose validity outlives its
  backend, device, configuration or operation.
- How an operation moves through validation, lock/ownership, observation,
  phase writes, cancellation and reporting. Check that dependencies and I/O
  boundaries remain readable and that diagnostics do not invoke command paths.
- Whether each helper, data object and abstraction has a concrete responsibility
  or removes real duplication. Look for pass-through layers, redundant flags,
  intertwined state machines and special cases that belong in a shared rule.
  Do not merge distinct facts merely to reduce a module's size.
- Whether an alternative genuinely reduces reasoning cost while preserving
  behavior, rather than replacing explicit code with a generic framework.
  Keep pure planning, bounded ownership and thin platform adapters; a new
  coordinator must not become a general service or plugin framework.

Before N2 implementation, compare the chosen design with the smallest viable
extension of the existing backend. Explain why its extra process, cache,
protocol or lifecycle state is required. Repeat the source assessment against
`v0.7.3` after the 0.8.0 changes, including every new observation/coordinator
module and platform adapter, so that historical cleanup does not excuse new
duplication.

Acceptance requires a disposition for each concrete finding: a separately
reviewable correction with an explicit behavior contract, or a specific reason
why the existing distinction is necessary. Structural simplifications preserve
external behavior; N0/N1 and any newly reproduced defect require a documented,
deliberate correction rather than an incidental change during refactoring.
Link relevant regressions to behavior; add tests only for missing coverage.
Require no known unresolved correctness issue at the final gate. Structural
changes need a clear before/after rationale and updated architecture boundaries,
not a target score, module count or line-count reduction. An assessment that
finds no additional defect can close with that supported result; do not refactor
for appearances. Keep review notes private; only resulting changes, public
contracts and necessary design decisions belong in the repository.

## N0: a shared observation model

Use a small pure observation primitive, shared by verification, the foreground
link barrier and the verifier's link-sync path. Keep expected values separate
from the last observed classification; removing an expectation after a match
must not make later reports invisible. Reuse register-aware numeric comparison.

Each path starts unobserved. A decoded nonmatching or invalid value revokes a
previous match; a later valid match can restore it. Undecodable packets remain
transport errors/omissions, not invented register values. State belongs to one
expectation set, observation window and backend/device instance; retries and
reconnects must not inherit an old confirmation without fresh evidence.

Distinguish a known contradiction from an absent report, an occupied receiver,
a receive failure and cancellation. A timeout must not turn a contradiction
into ordinary silence. Drain the current decoded delivery before deciding to
write: A=1, B=1, A=0 in a single bundle must not trigger a write inside the
callback after B. This does not make separately arriving packets atomic.

Known wrong link state must block dependent matrix writes, including the
background mix-reapply and timeout fallbacks. Bounded repair of PIN links is
allowed, followed by a fresh check. Pure silence retains a separately specified
backend-dependent fallback; never describe a timed wait as confirmation.
Carry failures through the existing refused/partial outcome with sent and
pending paths, and preserve the profile marker when the apply is incomplete.

Acceptance includes both standalone messages and OSC bundles, both link values,
match/contradiction/recovery permutations, duplicates, invalid values, partial
dumps, timeouts, stop requests and receive errors. Assert actual emitted phases
and mix-reapply counts, not only the observer's sets. Cover a contradiction in
the final message of a delivery and another read-back attempt. Preserve the
pure planner and acyclic runtime imports.

## N1: explicit write intent and REMEMBER ownership

Make these cases explicit at the current planner/apply boundary:

| Operation | REMEMBER | PIN |
| --- | --- | --- |
| Initial session application, including a full restart after hotplug | Write declared starting values once. | Apply declared values. |
| Explicit profile switch or explicit restore of the main desk | Write declared target values; verify the requested values strictly. | Apply and verify the target. |
| Repair after that initial application | Leave REMEMBER paths alone, including missing reports and values that previously matched. | Retry only according to the repair/observation contract. |
| Later selective reconcile, including reload or resume without a new session | Leave REMEMBER paths alone; unknown is not permission to reset. | Re-establish declared state subject to identity, mode and dependency checks. |

Use the effective policy, including `[pin]` overrides. Preserve all REMEMBER
paths after initial application, not just observed deviations. A previously
matching value can also change before the later write; it does not need a
redundant reset. An unknown preserved value must not be counted as a confirmed
match or an observed user adjustment. Keep those result categories distinct.

Do not implement this by changing only `_kept_by_the_device()`: that helper
also supplies summary counts. Separate write selection from classification,
and inspect `verify_and_repair()`, `reconcile_now()`, reload and mix reapply.
An explicit profile must still report applied/unverified if target values
cannot be confirmed; it must not borrow selective-reconcile semantics.

Account for stereo-partner effects and structural options overridden to
REMEMBER. If a dependent matrix write requires a link state that is retained
but unknown or different, refuse/skip that dependent operation with an exact
outcome instead of changing the retained setting or inventing confirmation.
Check indirect changes to retained channel values as well as filtered paths.

Acceptance: configured -6 dB, device -30 dB, missing/delayed/invalid feedback
must yield no later REMEMBER volume write, even when a different PIN register
needs repair. Include matching feedback, explicit PIN overrides, no receiver,
stereo partners, structural overrides, reload during startup verification,
profile persistence and full restart. Record initial-apply versus selective
reconcile behavior in the upgrade guide and amend ADR 0012 explicitly.

## N2: shared replies and coordinated writes with the existing mixer

Build on [ADR 0028](../decisions/0028-mixer-replies-and-writer-coordination.md).
The implementation decision must cover **both** reply distribution and writes
before either is declared complete. Prefer a measured upstream extension if
it can provide the whole contract; otherwise evaluate a narrowly scoped local
coordinator around the existing backend. Keep one chosen path, not two new
production transports. Any required backend/GTK patch is versioned, reproducible
and carried in artifact provenance; upstream acceptance is not assumed.

Settle these points in an ADR before implementing the coordinator:

- One owner for the exact UCX II/backend instance; register consumers before
  accepting work, invalidate all observations on backend/device replacement,
  and distinguish received order from device generation time.
- Replies reach separate consumers without `SO_REUSEPORT`. Bound subscriber
  count and queues; slow GUI/meter consumers cannot block verification. State
  loss or overflow is visible, not silently converted into a complete dump.
- Coordinate refresh requests and their observation windows so simultaneous
  consumers do not start overlapping hardware dumps. A cached write is not
  device read-back; cached observations require explicit freshness/provenance.
- Serialize a desk's link/barrier/matrix/channel operation as a whole against
  GUI writes. Define lock ownership/order, bounded leases, busy behavior,
  cancellation and what happens to input received while an apply is active.
  Never replay expired GUI commands or a failed request after reconnection.
- Treat physical knob changes as observations, not cooperating lock holders.
  Preserve REMEMBER and do not automatically fight each GUI change with PIN.
  Recheck identity, link dependencies and playback mode at write boundaries.
- Authenticate/authorize any new local control interface according to its
  actual transport. The existing loopback UDP backend does not gain user
  authentication because a coordinator exists. Identify bypass paths and
  claim serialization only for the paths actually mediated.
- Define failure and shutdown: a crashed consumer, coordinator or backend
  cancels pending work with known partial results. No stale confirmation,
  successful marker update, silent direct-write fallback or duplicate owner.

Acceptance uses the actual GTK executable with a simulated backend first:
both launch orders, two desk processes plus GTK, simultaneous refreshes,
mid-apply GUI edits, rapid reopen, replacement backend, missing replies,
overload and shutdown. Then qualify the chosen path on the UCX II. Exercise
source and native installations on GNOME, KDE and Xfce as applicable.
Fan-out alone does not close N2; the single-writer and lifecycle tests must
also pass. No new desk GUI screens are part of this work.

## N3: targeted requests and playback read-back

Investigate the pinned backend and device behavior through the existing
protocol implementation. First distinguish a request that produces a fresh
device response from a backend dump of values remembered after sends. Establish
whether individual register queries and genuine playback crosspoint read-back
exist, and measure their timing, completeness and effect on normal traffic.

If a reproducible backend change provides them, implement it at that seam,
record the exact patch/revision, and qualify the numeric/register model, N0/N2,
dump/diff/export and hardware paths before changing the release pin. A second
client or physical control must change the value independently when checking
whether the returned value represents the device rather than the writer cache.

Track investigation and delivered capabilities separately. A negative protocol
result can finish the investigation, but cannot close a promised read-back
feature or change `REESTABLISHED` to `VERIFIABLE`. If the planned capability
cannot be implemented, bring the concrete result back for an explicit scope
decision before calling 0.8.0 complete. Preserve existing measured behavior
until a replacement is actually demonstrated.

## N4/N5: additional Linux lifecycle targets

Keep one staged payload and a small adapter boundary for install, explicit
enable/disable, start, stop, reload, status, hotplug, resume and maintenance.
Select the real runtime user and device, preserve the shared lock permissions,
and target reload at the desk supervisor only. No adapter may run the mixer as
root to avoid solving permissions or redirect another user's session.

| Target | Deliverable | Required qualification |
| --- | --- | --- |
| Existing systemd/source and native targets | Preserve current behavior with the new runtime/coordinator. | Current matrix, real user-manager lifecycle and exact core/GTK version pairing. |
| Alpine/musl + OpenRC | Common source installation and supervised service adapter. | Real OpenRC VM, permissions/lock provision, explicit activation, disconnect/reconnect, reload, stop and maintenance recovery. |
| Void/glibc + runit | Common source installation and supervised service adapter. | Real runit VM, selected-user supervision, bounded restart behavior, hotplug/reload/stop and maintenance recovery. |
| NixOS | Pinned package expression and opt-in NixOS module. | VM build/activation, udev/permissions, writable user state, generation switch, reboot and rollback. |
| Fedora Silverblue | Qualified host RPM layering and activation instructions/integration. | VM deployment/reboot, maintenance state across deployment, update, rollback and removal. |

Pin exact image versions/digests and record libc, architecture and toolchains
before the implementation matrix is frozen. The existing seven source/four
native targets remain the regression floor. New prebuilt targets start with
x86_64; the source contract must not hard-code that architecture.

Each new adapter also needs boot without hardware, backend crash, repeated
attach/remove, suspend/resume hooks where provided, two competing software
writers and cancellation during a write. Test actual service managers rather
than accepting a successful container build as lifecycle proof. Maintenance
fences survive interrupted updates/reboots; configuration, profiles and marker
retain their owner and contents. Immutable hosts use their deployment mechanism,
not imperative writes into read-only system paths. Fresh installation remains
separate from enabling control of the hardware.

The platform starting points are the official
[OpenRC service guide](https://github.com/OpenRC/openrc/blob/master/service-script-guide.md),
[runit service documentation](https://www.smarden.org/runit/faq),
[NixOS manual](https://nixos.org/manual/nixos/stable/) and
[Fedora Silverblue overview](https://fedoraproject.org/atomic-desktops/silverblue/).
Validate the selected versions' integration details before adopting templates.

## N6: signed repositories and normal package-manager updates

Publish versioned APT and RPM repository channels for qualified targets.
Ubuntu 24.04, Fedora 44 and openSUSE Leap 16 already have native packages;
add native Debian 13 and Ubuntu 26.04 qualification from the existing source
matrix before publishing those DEB channels. Keep Arch's native package/recipe
and the verified source archive. Do not imply admission to official distro
repositories or turn `pip` into a second whole-product installer.

Choose an owned HTTPS publication endpoint and signing arrangement before
publishing. Record public fingerprints, scoped client trust, signing-key
storage/access, expiry, rotation and revocation/recovery. Keep private keys
and credentials out of source, logs and release assets. Prepare the whole
repository in staging before configuring production publication.

APT metadata uses repository-scoped trust following
[apt-secure](https://manpages.debian.org/stable/apt/apt-secure.8.en.html).
RPM channels require tested metadata and package verification with the target
manager, including the [DNF verification options](https://dnf.readthedocs.io/en/latest/conf_ref.html).
Use complete versioned snapshots and consistent index publication so a client
cannot observe new metadata before its packages. Keep core/GTK exact-version
dependencies, provenance, maintenance fencing and installation-before-activation.

Acceptance: clean subscription/install, actual 0.7.3 upgrade, explicit downgrade,
partial download/publication, interrupted package transaction, expired/wrong/
rotated key, altered metadata/package, and unavailable server. Use the real
APT, DNF and zypper paths for their channels; authentication failures must
refuse installation. Verify retention of configuration/profile/marker and
recovery of a stopped installation. Test both with and without GTK. A local
signed directory is preparation; N6 closes after clients verify the published
endpoint and perform the recorded transitions. Package updates do not imply
an in-product automatic updater or automatic hardware-state rollback.

## N7: compatibility, diagnostics and documentation

Keep accepted configuration syntax and source/manual operation. Document the
deliberate change to later REMEMBER writes, new coordination requirements and
backend identity. A new transport must negotiate/reject incompatible clients
before a write. Preserve existing exit/outcome meanings; version structured
output if its existing meanings must change. Status stays read-only and does
not turn a cached observation or exit 0 into a health/read-back certificate.

Update README, STATUS, INSTALLATION, UPGRADING, FEATURE-SURFACE, SECURITY-MODEL,
ARCHITECTURE and the relevant ADR amendments with the final implementation.
Keep profile omission semantics, partial writes, `READY=1`, strict explicit
profile verification and selective reconciliation distinct. Do not silently
mute omitted routes, persist GUI edits into config or promise a full snapshot.

Check current instructions against later evidence, not only old ADR openings.
For example, ADR 0013 already corrects the historical claim that only output
stereo flags are pushed: linked-partner changes and clock reports were also
observed. Preserve dated measurements and make current summaries unambiguous;
this is not a reason to add continuous reconciliation. Reassess the effective
service sandbox on the new hosts and distinguish cooperative write ordering
from protection against arbitrary local OSC clients.

## N8: completion and release acceptance

Use the [release checklist](../RELEASE-CHECKLIST.md) on the final candidate.
Keep the existing Python 3.9–3.14, strict type/lint/dead-code, architecture,
coverage ratchet, five-repeat, fresh full mutation, 200-cycle soak and repeated
fault gates. Record measured results and durations rather than prescribing a
larger test count. Extend mutation coverage to new decisions about confirmation,
retention, ownership and failure; do not weaken checks to admit the new path.

Add production-path regressions for N0/N1 and multi-process/real-GTK cases for
N2. Use failure injection at request, read, lock, phase-write and shutdown
boundaries; assert the actual emitted messages and outcomes. Complete the new
service/VM and repository matrices on the final payload, along with reproducible
builds, extracted-archive tests and actual 0.7.3 → 0.8.0 → 0.7.3 transitions.
Retain existing older-version transition coverage where it remains supported.

After the backend and routing code are final, qualify the UCX II with current
monitoring-state confirmation, phantom power off, quiet test levels and saved
restoration state. Measure routing, the changed link/REMEMBER behavior and any
new read-back claims. Record readable-state restoration and the known declared
routes separately. Run the final suite with the device physically off, then
verify automatic startup and restored state after reconnection. Keep each
artifact's device, firmware, backend and source identity accurate.

The release is complete only when required N0–N9 acceptance is met (or a scope
change has been explicitly agreed), the version/docs and package contents
agree, CI is green, and the downloaded source/packages/repository metadata have
verified provenance and signatures. Preserve old release artifacts. Do not
publish private reviews or GUI drafts with the release. No release date is set
until the backend-capability decision and repository hosting/signing inputs
are settled.
