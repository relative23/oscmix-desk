# 0.7.3: usability and existing-mixer integration

**Status: released as 0.7.3, 2026-09-24.** R0–R7 are complete;
[versioned evidence](../evidence/0.7.3/) records the software, installation,
desktop and hardware acceptance results. This plan builds on released 0.7.2 and targets UCX II users
across Linux distributions. The existing upstream GTK mixer is distinct
from the deferred desk desktop application.

## Starting point

- The README's profile introduction used a complete-snapshot analogy,
  although profiles declare partial state. Its verification explanation
  also implied equality of every reported value. Correct both descriptions
  while preserving the existing runtime semantics.
- [`verify._report()`](../../src/oscmix_desk/verify.py) already logs
  retained REMEMBER values separately. Its success summary counts
  confirmed and unobserved settings, but does not include retained values
  or distinguish never-reportable state from a missing report.
- [`launcher.py`](../../src/oscmix_desk/launcher.py) polls desk ports, then
  executes GTK without connection arguments. At pinned backend revision
  `f2fdd5ec78338848754aad32cc07f3440de63395`, `gtk/main.c` reads its own
  GSettings `send-host`, `send-port`, `recv-host` and `recv-port`. Desk and
  GTK settings can therefore disagree. The launcher also consults a
  profile's old machine settings although current profiles inherit the
  main desk's machine identity.
- The launcher attempts a systemd start before resolving the GTK binary.
  The installed manual path and missing desktop resources need deliberate
  handling. A listening UDP port alone is not backend/device identity.
- [`build-package.py`](../../scripts/build-package.py) and
  [`stage-install.sh`](../../scripts/stage-install.sh) already support
  optional GTK payloads. The published native packages qualify the
  headless path; existing build support is not desktop qualification.
- The pinned backend sends replies to one configured destination. GTK
  and desk currently compete for the receive port; direct GTK/OSC writes
  do not participate in the desk lock. Receiving the same reports and
  serializing writes are two distinct integration requirements.

## R0: classify the latest received report in the open window

**Confirmed correctness defect; first release blocker.** In 0.7.2,
`verify._absorb()` ignores a path after its first matching report. A
socket-free reproduction through the public `verify_routing()` entry point
requests `/output/5/stereo = 1` and `/output/7/stereo = 1`, then feeds:

```
/output/5/stereo = 1
/output/5/stereo = 0
/output/7/stereo = 1
```

Both paths incorrectly end in `confirmed`, with no mismatch or PIN repair
problem. This occurs with a single listener batch and with three separate
batches while the window remains open. The wrong-then-right,
right-wrong-right and wrong-only controls behave as expected. These are
local fake-backend reproductions with sockets and subprocesses forbidden,
not a claim of a measured hardware occurrence.

Use the latest decoded report for each expected path **received within
the observation window**. A mismatch removes an earlier confirmation;
a later match removes an earlier mismatch. The sets remain disjoint.
A decoded report with unusable numeric arguments must not leave a stale
confirmation intact. Preserve callbacks, the shared dump, the bounded
deadline, cancellation and cleanup. Correct the callback documentation:
it runs for each received report, not only the first report of a path.

**Acceptance:** regress both report orders, repeated toggles, duplicates,
interleaved paths and listener batches. A differing PIN remains a repair
problem; a differing REMEMBER value is classified as a mismatch and then
retained by policy, never counted as equal. Exercise callers' startup,
reconcile and strict profile outcomes, including mix reapply and stop.
Use an independent last-received-value oracle for generated sequences.
No claim of an atomic snapshot or detection after the window closes:
UDP arrival order does not establish when hardware produced a value.

## R1: make verification summaries precise

Use the existing comparison, policy and reportability functions to report
matching values, deliberately retained REMEMBER differences, expected
reports that did not arrive, and values this backend cannot report.
Keep actual mismatches and read/bind failures visible. A policy-compliant
result is not proof that the entire device equals a configuration.

The startup/reconcile summary and the outcome of an explicit profile
switch have different contracts. Do not relax a profile's strict
confirmation criteria or change public outcome states/exit codes merely
to harmonize wording. Update README, troubleshooting and examples with
the resulting messages.

**Acceptance:** existing pure/fake-backend tests exercise mixed PIN and
REMEMBER differences, overrides, missing prompt/slow reports,
unreportable playback, empty observations, retry and port failure. Summary
counts and path lists agree with the actual classification, including
the case where REMEMBER differs and policy reconciliation succeeds.

## R2: make launching the existing mixer predictable

Resolve the GTK executable and required schema before any service-start
attempt. Inspect an existing manual backend without trying to create a
competing systemd session. If none is running in manual mode, explain the
foreground start command; preserve explicit activation and maintenance
fences for native installations.

Resolve the effective main desk's machine settings and associate a
backend with that exact interface using existing identity helpers.
Replace obsolete active-profile port fallback behavior. Check the GTK
connection settings against that backend, including custom ports and
non-loopback saved hosts. Give an actionable mismatch message; never
silently overwrite a user's persistent GSettings or attach to an
unrelated UDP listener. Missing optional desktop tools must produce a
clear diagnostic rather than adding dependencies to the core.

**Acceptance:** fake-process tests cover default/custom ports, a stale
profile, an unrelated listener, a missing GTK binary/schema, manual mode,
unavailable user manager, disabled native activation and a maintenance
fence. A desktop smoke test confirms the GUI connects to the intended
fake backend and actually receives state.

## R3: one runtime status command

Add `oscmix-session --status`, available in source and native installations,
with human-readable output and an explicitly versioned `--json` form.
Keep installer preflight and `oscmix-setup --check` for their existing
installation tasks; reuse helpers rather than create a second discovery
or validation implementation.

Report the running/resolved installation and backend provenance,
effective config and selected profile, exact device/serial, service or
manual-session status, active USB playback observation, receive-port
availability, and installed GTK resources. A remembered profile name
does not establish current hardware agreement. Service readiness is
separate from verification: `READY=1` can precede completion of the
background read-back. Do not infer a verification result from service liveness or
an old journal line. Distinguish unavailable information from a measured
failure and identify the next useful action.

**Acceptance:** the command makes no OSC requests/writes, does not bind
the reply port, opens no audio stream, starts no service and changes no
files. Offline and manual operation work. Port/process observations are
point-in-time diagnostics, not a guarantee that a later operation will
succeed. JSON has stable field/status meanings and handles missing
permissions, malformed procfs/config data and absent optional tools.

## R4: ship the upstream GTK mixer as an optional companion

Use the shared staging/build path and the existing backend pin. Prefer a
separate optional companion package with an exact compatible core-package
dependency and distinct file ownership. Decide package names/dependencies
before publishing: a GTK variant must not overwrite an installed core or
bundle a second competing backend. Keep desktop dependencies out of the
headless package.

Cover the four existing native targets: Ubuntu 24.04, Fedora 44,
openSUSE Leap 16 and Arch. Include GTK runtime dependencies, compiled
schema handling, desktop entry and icon. Preserve explicit service
activation, migration backups and package-update recovery.

**Acceptance:** fresh install, add/remove companion, upgrade/downgrade,
source migration and interrupted-update recovery preserve desks, profiles
and activation state. Build all package targets, check payload ownership,
repeat builds and verify checksums/attestations. Exercise actual desktop
launch/connect/close using an isolated backend on GNOME and KDE Wayland
and Xfce/X11; record the environments actually used. Installing or removing
the companion must not itself start a mixer or apply a default desk.

## R5: make GUI/read-back contention actionable

Test GUI-first and desk-first operation against the actual pinned GTK
receiver and an isolated backend. Show which operation cannot read back
and the configured port; name a process only when its identity is known.
Document an explicit close-GUI, retry/read-back, reopen-GUI workflow.
Preserve REMEMBER values through recovery and distinguish a profile
switch that wrote without confirmation from a reconcile that wrote
nothing. Do not kill the GUI, steal its socket or silently replay an
earlier write request.

**Acceptance:** occupied-port and real bind failures retain their different
outcomes; closing the GUI releases the port and a deliberate retry works.
No missing dump is counted as confirmation. Verify that callbacks and
cleanup do not leave another listener or backend behind.

Before implementing simultaneous read-back, write a design decision for
upstream subscriptions versus a local reply distributor: ownership,
startup/shutdown, loopback binding, freshness, missing packets and device
identity must be explicit. A different port or `SO_REUSEPORT` alone does
not provide every consumer with every reply. A reply distributor also
does not make GTK writes take the desk lock. Any backend/pin change or
new long-running broker requires separate implementation and
qualification scope; 0.7.3 must not claim to have solved it through
diagnostics alone.

## R6: show what a profile transition leaves undeclared

Extend the existing `--dry-run --profile NAME` preview, rather than add a
second profile parser or apply mechanism. Compare the current effective
desk's declarations with the requested profile through the shared pure
desired-state logic. Identify previously declared route crosspoints for
which the target supplies neither a replacement nor an explicit mute.
Explain link/partner effects where a link change can also affect a route.

This is a comparison of declarations, not an inventory of all audible
hardware routes. A new invocation cannot discover unknown playback cells
from the unreadable matrix. Do not call every partial profile invalid,
mute omitted routes automatically or claim that every undeclared cell
is unaffected by writes to its linked partner.

**Acceptance:** an A-to-B example retains an omitted route unless B
explicitly mutes it. Cover overlapping routes, changes of pair/link
state, invalid targets and missing/stale active markers. Preview sends
nothing, changes no profile marker and identifies which two configurations
it compared. Reuse the existing offline preview behavior.

## R7: release acceptance and ordering

1. Correct the documentation; fix R0 and prove the contradictory-report
   regression fails on 0.7.2 and passes on the candidate. Implement R1
   and R2 with focused regressions before convenience work.
2. Build R3 and R6 from existing helpers and finalized result descriptions.
3. Qualify R4 together with the R5 contention/recovery scenarios.
4. Run the established [release checklist](../RELEASE-CHECKLIST.md) on the
   final candidate. Retain Python, coverage, mutation, repetition, soak,
   installation and publication gates. Exercise real-version
   0.7.2 upgrade/rollback and preserve prior evidence identities.

Keep coverage scopes explicit: the existing runtime/entry-point percentage
does not represent all packaging and helper code. Report their separate
behavioral/lifecycle checks. Review surviving mutants in the changed
classification and activation/recovery paths for missing assertions;
neither a larger global percentage nor killing equivalent mutants is a
substitute for the sequence and failure tests above.

This scope is not itself a release result. Hardware tests require a quiet
test setup. The config format, PIN/REMEMBER behavior and
backend pin stay fixed unless a separately validated defect requires a
reviewed change. Own-GUI implementation and physical dual-device work
remain deferred. New init adapters, immutable-system packaging, package
repositories and other device models keep their existing entry conditions.
